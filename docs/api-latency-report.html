The cheapest thing this API can do takes 86 ms

Every GET route timed against the running API. A handful are slow enough to fix on their own, but the number underneath them all is the one worth knowing: nothing here answers in under 86 ms, and most of that is spent opening database connections the request then throws away. The median endpoint is 134 ms — the gap between the cheapest response and the typical one is smaller than what either spends before running a query.

What an empty request costs

Timed directly rather than inferred. A PostgreSQL connection costs 34 ms on this machine, and most endpoints open two — one for the content database, one for the accounts database that turns created_by into a name. Against an 86 ms cheapest response, that is most of the bill before a query has run.

Connecting to genshin_impact — 34.3 ms Connecting to users — 34.3 ms Composer autoload — 2 ms A seven-row query — 1.8 ms

Opening the same connection with PDO::ATTR_PERSISTENT measured at 0.0 ms after the first. That is around 69 ms available on nearly every authenticated request, for a configuration change. It is not free of consequences: a pooled connection carries its session state between requests, so anything that sets a session variable or leaves a transaction open becomes everyone's problem. This codebase does neither, which is what makes it worth trying.

The remainder — PHP starting, requiring the endpoint files, registering 406 routes, routing, encoding the answer — is not broken out here because it cannot be timed cleanly from inside the request it belongs to. It is what is left of the 86 ms once the four measured pieces above are taken out.

Slowness is not payload

Response size against response time. If big answers were the problem the points would form a line. They do not: the slowest endpoint in the API returns almost nothing, and the largest response is three times faster than it.

What is broken

Found by the measurement rather than looked for: routes that cannot succeed, and one that cannot be called.

Eight routes point at two tables that do not exist

/api/affiliations and /api/characters-affiliations return 500 on every call, in all four methods. Neither table was ever created — a character's affiliations live in a JSON column on characters instead. The routes have been registered and failing since.

Either drop the endpoints or create the tables; both are cheap, and leaving a route that only ever 500s is not.

GET /api/stats/{id} cannot ever match a row

It runs SELECT * FROM stats WHERE id = ?, and stats has exactly one column: name. The route pattern also requires digits, so even the right value could not reach it. Its sibling /api/stats works and is what the site uses.

/api/characters-voice-overs returns 47.5 MB in one response

Every voice line for every character, unpaginated, including the full translated text in five languages. It is not slow for its size — 930 ms for 47 MB is respectable — but nothing should ever need all of it at once, and a browser asked for it twice will feel it.

/api/dashboard/stats is 2 seconds of counting

Seventeen queries, several of them full counts over the largest tables — counting the 111,000 audit rows alone is 43 ms. It returns almost no data for the time it takes, which is the signature of a page built from many small questions rather than one.

It no longer loads on opening the admin panel, which took the sting out of it, but it is still the slowest thing here.

Three routes answer 404 to a well-formed request

/api/files, /api/files/raw and /api/migrations/file need query parameters this measurement does not know how to supply, so they were called bare and refused. They are not broken — they are the routes a path-shaped harness cannot reach, and they are listed here so the failures in the table are not read as defects.

Nothing else is slow

Once the cheapest cost and the handful above are set aside, the rest span 86 ms to 188 ms — a range narrow enough that it is measuring the framework, not the queries. There is no scattered problem to hunt.

What I would change, in order

Try persistent connections

One option on the PDO constructor, worth about 69 ms on every authenticated request. Measure again afterwards — the win is only real if the connection is genuinely reused, which depends on how PHP is served in production rather than on the code.

Only open the accounts database when a response needs it

Half the connection cost is usersDb(), opened so that created_by can be shown as a name. Public read endpoints that never expand those columns are paying 34 ms for nothing.

Page the four largest collections

characters-voice-overs, enemies-drops, enemies/full and weapons/full account for 78 MB between them. Everything else in the API is under a megabyte.

Delete the routes that cannot work

Nine of them. They are not a performance problem; they are a correctness one that this measurement happened to find.

How this was measured

  • Every GET route in the generated API spec, called against the running PHP development server on this machine, signed in as an administrator.
  • Two warm-up calls, then seven timed calls per endpoint; the median is reported, with the fastest and the 95th percentile beside it.
  • Path parameters were filled from each resource's own collection, so /api/artifacts/{id} was called with a real artifact rather than a shared id that would have returned 404.
  • Endpoints that walk the asset tree or the backup folder were called once rather than sampled, and are excluded from the distribution — averaging a filesystem survey with a lookup table would flatter both.
  • The floor is the median of the cheapest endpoint measured, not a separate synthetic request: it is the fastest the API was actually observed to answer anything.
  • Thirteen routes could not be called at all, because nothing exists to put in their path.
  • Reads only. Timing writes would mean creating and destroying an entity per sample, which measures the fixture rather than the endpoint.
  • A development server on a workstation, not production. The shape of these numbers travels; the absolute values do not.
